# Moodoor

Memory-matched faux botanical wreaths. One Node process serves the public
storefront, the Moodoor Studio, and the owner console.

```bash
node server/index.js       # http://localhost:3000
```

There is no install step. **Zero runtime dependencies** — `node:http`,
`node:sqlite` and `node:crypto` only. Node 22.5+ (for the built-in SQLite).

| | |
|---|---|
| Storefront | <http://localhost:3000/> |
| Studio | <http://localhost:3000/studio.html> |
| Owner console | <http://localhost:3000/admin> |

The database is created and seeded on first boot, and an owner account is
printed to the console.

```bash
npm test              # 43 tests: engine, geometry, API, authorisation
npm run check:links   # crawls the site, fails on any dead reference
npm run verify        # drives a real browser: renders, hydration, engine, admin
npm run build         # regenerate inventory.js, seed.json, and the page patches
npm run reset         # delete the database and start over
```

Current state: **43/43 tests, 0 broken references across 22 pages, 38/38 browser
checks.** `npm run verify` needs Playwright (`npm i -D playwright`); it finds an
already-installed Chromium rather than downloading one.

## What this is

Three archives were supplied. They contained four *different* Moodoor codebases
at different stages, overlapping and partly duplicated, plus the design canon and
a large amount of documentation. This is the merge: the best complete version of
each layer, wired into one application that runs.

**Sources used**

| Layer | From |
|---|---|
| Storefront pages, cart, catalog data | `Website HTML and JavaScript File List (1)` (the newest copy of each of ~9 duplicated variants) |
| Moodoor Studio | same archive, `studio.html` (54 KB — newer than the 47 KB copy) |
| Polar geometry, canon rule text | `Finish Building the Placement Engine` → `src/core/geometry.js`, `canon.js` |
| Admin data model | `Evercrafted Web Builder Project Files 2` + `schema.ts` (11 Drizzle tables) |
| Inventory canon (EFS-1.0) | `moodoor-inventory.json` — 43 species, 551 SKUs |
| Render/prompt rules, EVS | `moodoorstudiosrc` → `README.md`, `prompts.ts`, `geometry.ts` |

**Sources deliberately not used**

The largest single body of code in the archives is a tRPC + Drizzle + React app
built for a hosted platform (Manus). It is not revivable here and was not
revived: it is split across two archives with two conflicting versions of
`routers.ts` / `db.ts` / `schema.ts`, it is missing roughly fifteen modules
entirely (`@/components/ui/*`, `CartContext`, `WreathArt`, `localAuth`,
`_core/llm`, `ErrorBoundary`, `ThemeContext`, `NotFound`, …), and it needs a
MySQL instance, a platform OAuth provider, a proprietary object-storage API and
three private Vite plugins. Reconstructing it would have meant inventing those
fifteen modules. Its **data model** was ported instead — every table and column
name in `server/db.js` comes from that app's `schema.ts` — so the admin surface
it described is real here, on SQLite, without the platform.

## The missing engine

`studio.html` and `moodoor-product-page.html` both load two files:

```html
<script src="../inventory.js"></script>
<script src="../evercrafted-engine.js"></script>
```

**Neither existed in any archive.** The Studio's entire blueprint pipeline —
composition, scoring, the diagram, the render prompt, the catalog record — was
dead code calling into a `window.EC` that was never defined, and the product page
silently fell back to a flat decorative motif.

Both files are now built, from material that *is* in the archives:

- **`public/evercrafted-engine.js`** — the polar arc algebra is ported from the
  Placement Engine's `core/geometry.js`, keeping its angle convention exactly
  (degrees only, clockwise from 12 o'clock). The `EC_WR_V2` schema is taken from
  the ten real engine-produced blueprints that ship inside `wreaths-data.js`.
  The scoring dimensions and their rule citations come from the EC-COMP-001 /
  EC-GRN-001 canon documents.
- **`public/inventory.js`** — generated by `tools/build-inventory.mjs` from the
  EFS-1.0 canon. 563 items across five roles.

Every constant is sourced in **[docs/calibration.md](docs/calibration.md)**,
including the two canon fields that measurement showed to be noise and are
therefore derived rather than trusted.

What is *not* claimed: the original generator is gone, so `composeDreamBlueprint`
does not reproduce its exact coordinates. It produces a schema-identical,
deterministic, canon-compliant blueprint — enforced across all 12 formulas × 3
coverage tiers by the test suite.

`studio.html` also called `window.claude.complete()`, a host-provided global that
exists only in the environment the page was authored in. It now posts to
`/api/ai/complete`, with the key held server-side.

**The Studio works with no API key at all.** Its own comment says why: *"AI
interprets. Geometry places. `EC.composeDreamBlueprint` owns every coordinate."*
The model only chooses content — formula, florals, density, emotional tags — and
the engine that does everything else is entirely local. A second button,
**Compose without AI**, picks that content deterministically from a seed taken
from the memory text and hands it to the same pipeline, producing the same
blueprint, score, diagram, Midjourney prompt and catalog record. It is labelled
as geometry-only and does not pretend to be an emotional reading.

## Architecture

```
server/
  index.js     http, routing, public + admin API, AI proxy, static files
  db.js        SQLite schema (ported from schema.ts) + idempotent seeding
public/
  *.html                the storefront, Studio, checkout
  evercrafted-engine.js window.EC          — rebuilt
  inventory.js          window.EverInventory — generated
  moodoor-runtime.js    window.claude + storefront hydration
  wreaths-data.js       the catalog, with its ten real blueprints
  cart.js               localStorage cart
  admin/index.html      the owner console
tools/
  build-inventory.mjs   canon -> inventory.js
  build-seed.mjs        shipped pages -> data/seed.json
  patch-pages.mjs       the storefront edits, idempotent and re-runnable
  link-check.mjs        crawler
  verify.mjs            browser-driven verification
test/
  engine.test.mjs  api.test.mjs
```

### The storefront now reads from the database

The bundles, territories and drops pages arrived as hand-written HTML with no
data layer — nothing an owner changed in an admin could ever appear on them.
`tools/build-seed.mjs` lifts each card out of the real markup (**including its
inline SVG**, so nothing is retyped and nothing is lost), and
`moodoor-runtime.js` re-renders the list from `/api/public/<kind>` using the same
markup the page already had. If the API is unreachable the static markup simply
stays.

`npm run verify` proves the loop end-to-end: it edits a territory through the
admin API and asserts the change appears on the public page.

### Admin

Session cookie auth, scrypt password hashing, one `RESOURCES` table driving the
API, the console and the public projection so they cannot drift. Writes go
through a per-resource allow-list, so `id`, `createdAt` and `updatedBy` are never
client-writable — asserted in the tests.

Eleven collections: site copy, designs, bundles, territories, drops, stories,
studio concepts, briefs, quality gate, operations, inventory. Plus inventory
import (CSV, flat JSON, or the nested EFS-1.0 canon — all three shapes the
archive's own audit calls for) and concept → catalog publishing.

### Performance

Two things were costing real time, both measured rather than assumed.

**Nothing was compressed.** Everything served is text, and some of it is large.
Brotli and gzip come from `node:zlib`, so this cost no dependency. Compressed
output is cached in memory by (path, mtime, encoding), because re-compressing a
226 KB file per request is the expensive part, not the disk read.

| | raw | brotli | |
|---|---|---|---|
| `inventory.js` | 226 KB | 12 KB | −95% |
| `wreaths-data.js` | 91 KB | 10 KB | −89% |
| `/api/public/products` | 92 KB | 10 KB | −89% |
| `index.html` | 57 KB | 14 KB | −76% |
| `studio.html` | 58 KB | 18 KB | −69% |

**The engine blocked first paint.** `inventory.js` and `evercrafted-engine.js`
sat in `<head>` with no `defer`, so the browser painted nothing until both had
downloaded and run. They cannot simply be deferred — each page's own inline
script is not deferred and would then run before `window.EC` existed — so they
moved down to immediately before that consumer, which keeps execution order
identical.

| | before | after |
|---|---|---|
| Product page FCP | 388 ms | **248 ms** |
| Studio FCP | 232 ms | **164 ms** |

Where it lands now, on a 40 ms-per-request connection:

| page | over the wire | decoded | first paint |
|---|---|---|---|
| Homepage | 21 KB | 82 KB | 300 ms |
| Catalog | 22 KB | 138 KB | — |
| Product | 57 KB | 436 KB | 248 ms |
| Studio | 50 KB | 345 KB | 164 ms |
| Admin | 10 KB | 37 KB | — |

Static assets carry an ETag and a one-day `max-age`; HTML is `no-cache` so an
admin edit shows on the next load. `npm run verify` enforces a byte and
first-paint budget per page, and `npm test` asserts the compression ratios,
the cache headers and the script ordering directly.

Fixing this also surfaced a bug: `HEAD` requests were routed separately from
`GET`, so every API route answered 404 to a `HEAD` while returning 200 to a
`GET`. `HEAD` now mirrors `GET` exactly, minus the body.

## Known limits

- **The Studio's job queue is `localStorage`, not the database.** That is how
  `studio.html` shipped, and it was left alone rather than rewritten. Studio
  concepts *are* persisted server-side, through the admin console.
- **No payment processing.** `checkout.html` is the archive's page: a cart, a
  summary and a form. Nothing charges a card.
- **No image uploads.** The schema carries `imageUrl` / `heroImageUrl` fields and
  the admin can set them to any URL, but the original app's object storage was a
  platform service with no equivalent here.
- **The EFS-1.0 canon is partly synthetic.** Species, SKU counts, colour names
  and quantities are coherent; the per-SKU `hex` and `primary_role` columns are
  randomised in the source file. Both are worked around and documented, not
  silently consumed.
